## R12 — High: postcard displays a QR placeholder but never starts its upload — OPEN

Confirmed by source inspection in **both** the baseline and our current candidate. The `Printing` dispatcher selects `PostcardPrinting` for `shootType === 'postcard'`. That component renders `DownloadQR` from `cloudToken` and performs physical printing, but has no `uploadSessionToCloud` or `setCloudToken` call. The shared `usePrintFlow` handles progress, settlement and navigation; it does not upload. Other token writers are in the separate product components, not a global fallback. A new session starts with a null token, and `DownloadQR` needs a token before displaying a real download link.

Therefore, a clean postcard session in this source has no route to create its QR, even on healthy internet. This closely matches the new report, but is not yet an observed reproduction on the studio's running build. The previous 242 passing twin checks and 27 targeted kiosk checks did not exercise every product's complete print-to-upload path. Our prior patch fixes many upload/recovery boundaries but **does not fix this missing caller**. This is a gap in the earlier review and a release blocker.

Read-only inventory: `node audit/review-product-upload.mjs` returns exit **2** for an open source gap. Output: `audit/product-upload-coverage.json`. Photo, calendar, photo-ID fallback and l'INCONNU each have an upload call; postcard has none. This inventory is not a browser test or a complete call graph. Manual inspection of the shared hook, thank-you page, dispatcher and token writers supplies the cross-component evidence.

### Proposed fix

1. Add postcard to a session-owned digital-delivery controller, preferably shared with other products to prevent another omitted product. Prepare the correct landscape postcard download image independently of the printer-only 90-degree rotation. Preserve current colors, segmentation, filters and chosen photos.
2. Capture the original session epoch before preparation. Start the existing bounded photo upload, set the current session token after durable confirmation, and reuse the existing same-photo/token recovery. Survive printing-screen unmount; reject results after an actual customer reset.
3. Keep QR retry separate from printing and payment. Retrying a download must never call `callPrint`, capture payment again or start a new consent/session identity.
4. Add actual component/route coverage for every product, with healthy, delayed, failed and retried delivery. Explicitly include postcard mount → print complete → `/bye` → token/QR, StrictMode, next customer and no-QR choices. All physical/payment/relay operations must be replaced locally.

## Preparation is a separate delay path from network upload

In the saved photo/calendar/l'INCONNU flows, `await composeShareVideos(...)` happens **before** `photoBlobForUpload(...)` and `uploadSessionToCloud(...)`. The wrapper serially prepares layout video, then the Story. The lower-level uploader commits the photo before handing videos to the bridge, but it cannot begin until that preparation returns.

The two compositor `once(...)` helpers wait for media events without a timeout or cancellation; layout seeks assign `currentTime` before installing `seeked` listeners. Story creation assigns `currentTime = 0` and awaits `seeked`, even if no effective seek happens. A missing/already-fired event or blocked rendering can therefore leave preparation pending. This is a confirmed unbounded-wait design in the saved code; whether it caused Claire's incident is **unverified**. The current thank-you preparation watchdog offers help, but does not make a stalled compositor complete or produce the missing postcard upload.

### Proposed fix and local tests

- Publish the prepared photo/QR before optional video work completes. Record the intended video state explicitly so the phone can wait within the existing persistent video clock. Do not derive video intent only from blobs that must already exist. Later video delivery must retain the same token, media ownership checks, metadata persistence and expiry rules.
- Bound load/seek/play/record/stop waits, register event listeners before starting the operation, check already-ready/already-at-target states, handle media errors explicitly, and cancel/clean up streams, elements and object URLs. A video failure must leave the photo usable and report an honest optional-media state.
- Instrument photo render/JPEG, layout creation, Story creation, sign, photo body, durable confirmation and queue handoff separately. Distinguish elapsed preparation, queue wait, network transmission and retry/backoff.
- Simulate never-fired media events, same-position seeks, failed playback, stalled recorder stop, background/resumed tab, slow CPU and reset while composing. Assert photo QR readiness without waiting for optional video and no cross-customer token/bytes or duplicate print/payment. Repeat after idle with the already-prepared network/storage faults.

## Sample size and video timing

At an **assumed**, uncongested 1 Mbit/s upload, transferring 1.7 MB takes roughly 14 seconds before request overhead. The default video worker cap is 50 KiB/s: about 0.94 MB of video takes roughly 19 seconds of transmission, plus queue wake-up, signing, confirmation, congestion and retries. These are arithmetic comparisons, not measurements of the studio. One successful session's delivered files do not reveal a failed session's preparation time, original uploads or queued backlog.

Locally saved WhatsApp copies were inspected with ffprobe:

| Sample | Size | Duration | Frames / average rate | Largest gap between decoded frame timestamps |
| --- | --- | --- | --- | --- |
| Stacked moving portraits | 707,138 bytes | 5.030 s | 80 / 15.90 fps | 908 ms |
| Card over blurred moving background | 61,673 bytes | 2.393 s | 25 / 10.45 fps | 1,033 ms |

Both delivered copies are H.264, 480×848. Timing irregularity is measurable in these copies, but variable frame rate, intentional holds and WhatsApp recompression prevent attributing it to the original compositor. The reported original sizes differ from the WhatsApp copies. The saved compositor requests an 8-second layout and at most a 6-second Story; these copies alone do not identify the active code, an original truncation or the reason for shorter durations.

Reproduce the timing analysis with `node audit/analyze-media-timing.mjs <local-main-video> <local-story-video>` (requires an existing ffprobe). Committed evidence includes only technical measurements in `audit/media-timing-2026-11-02.json`, not customer media, file paths, tags or conversation exports. Deleting one small video is not the primary fix for a missing upload caller or an unbounded preparation wait.
